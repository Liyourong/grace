## 账号与访问

### 01 邮箱注册、验证码与重发

**01.1　什么时候才算注册成功？**

用户输入正确的六位邮箱验证码后，后端才在一个数据库事务中创建账号、登录凭据和首个会话。SendGrid 接受发信请求时，数据库里只有待验证记录。

**01.2　用户收到两封验证码邮件，该用哪一封？**

同一次注册的重发沿用原码，所以两封都可以用。重发至少间隔 60 秒，每次注册最多发五封。若重新发起注册并签发新码，则要用新码。

**01.3　验证码会在 60 秒后失效吗？**

60 秒是重发冷却时间。当前版本会限制输错次数，但验证时没有检查验证码年龄。如果要设置十分钟有效期，就要记录签发期限，并在验证事务中检查。

依据见[注册流程](../backend/src/auth/mod.rs)、[邮件发送](../backend/src/auth/email.rs)、[验证状态](../backend/src/auth/store.rs)。

### 02 密码登录、会话与登出

**02.1　为什么登录后切换应用 Pod 仍然有效？**

浏览器带着会话 Cookie，任一 Pod 都能从 PostgreSQL 查到相应会话。服务端核对令牌摘要和有效期，因此入口无需把用户固定到第一次登录的 Pod。

**02.2　为什么密码和会话令牌使用不同的存储方法？**

人选的密码容易被猜，所以我们用带盐的 Argon2id 增加每次猜测的成本。会话令牌由系统随机生成，数据库保存摘要，收到令牌后可快速查找对应会话。

**02.3　在手机上登出，电脑也会被登出吗？**

登出会删除当前 Cookie 对应的服务端会话。手机与电脑分别登录时各有一个会话，因此手机登出后，电脑上的会话可继续使用，直到它过期或被撤销。

依据见[密码与 Cookie](../backend/src/auth/rules.rs)、[会话存储](../backend/src/auth/store.rs)。

### 03 私有试卷与用户数据隔离

**03.1　服务器怎样知道这份卷子属于谁？**

后端先从会话得到用户 ID，再同时按试卷 ID 和所有者 ID 查询。读取其中一道题时也要经过所属试卷的检查。浏览器传来的试卷编号只负责定位资源。

**03.2　把试卷移入文件夹时，如何保证两者属于同一人？**

更新语句先限制试卷所有者，数据库再用所有者 ID 和文件夹 ID 这一对值检查外键。因此即使客户端选错目标，也不能把试卷移入另一个账号的目录。

**03.3　已有测试怎样验证用户隔离？**

集成测试建立两个独立账号。一个账号创建试卷和文件夹，另一个账号读取或修改这些资源时请求会被拒绝。测试还会检查对方的题库列表，确认私有内容没有出现。

依据见[试卷查询](../backend/src/papers/store.rs)、[文件夹约束](../backend/migrations/0005_paper_library.sql)。

### 04 浏览器请求保护

**04.1　浏览器已经带了 Cookie，写请求为什么还要检查 Origin？**

Cookie 说明请求关联哪个会话。Origin 说明浏览器从哪个站点发起请求。Grace 对修改状态的请求核对白名单，避免其他站点借用用户已有的会话触发操作。

**04.2　HttpOnly、Secure 和 SameSite 各保护什么？**

HttpOnly 限制网页脚本直接读取会话 Cookie。云端的 Secure 要求浏览器通过 HTTPS 传输它。SameSite=Lax 限制部分跨站请求携带 Cookie，配合服务端的 Origin 检查使用。

**04.3　如果应用换了域名，为什么首页能开却无法提交答案？**

首页是读取请求，提交答案会经过 Origin 检查。如果新域名还没加入应用配置，写请求会收到 403。应核对实际浏览器来源和部署中的 APP_ORIGINS。

依据见[请求中间件](../backend/src/main.rs)、[请求解析](../backend/src/common.rs)、[Cookie](../backend/src/auth/rules.rs)。

### 05 演示账号与运维授权

**05.1　固定演示验证码会给用户运维权限吗？**

不会。固定码只对配置的演示邮箱生效，用来走注册流程。运维权限由另一条数据库授权记录决定，后端在每次访问受限接口时检查它。

**05.2　应用如何识别已有的共享测试账号？**

启动时读取预置密码哈希。对已有账号，只有指定用户名和数据库中的凭据都与预置值匹配，才会补上运维授权。保留原数据库也能保留该账号的题库和进度。

**05.3　正式运营时，共用一个运维账号有哪些代价？**

多人用同一身份时，很难区分具体操作者，也难以单独撤销某个人的权限。正式团队可以给每人独立账号，再分别授予运维角色。

依据见[演示邮箱](../backend/src/auth/email.rs)、[共享账号授权](../backend/src/auth/store.rs)、[运维权限检查](../backend/src/devops.rs)。

## 试卷与界面

### 06 初始试卷

**06.1　六份初始试卷是什么时候发放的？**

首次读取个人题库时，后端检查该账号的领取记录，并补发缺少的目录项。六份包括 French Basics 和五份语法练习。这样，已有账号也能通过同一入口领取缺少的内容。

**06.2　两个标签页同时第一次打开题库，会得到十二份吗？**

每个账号对每个目录项只有一个领取位置。数据库唯一约束保证同一项只有一个请求能取得领取资格，只有该请求会在事务内写入试卷。集成测试覆盖了并发首次访问。

**06.3　为什么用户删除了初始试卷，下次登录也不会重新出现？**

删除试卷时仍保留该目录项的领取记录。后端下次检查的是是否领取过，因此会尊重用户的删除操作。

依据见[发放逻辑](../backend/src/papers/store.rs)、[领取记录](../backend/migrations/0005_paper_library.sql)。

### 07 JSON 试卷导入与校验

**07.1　为什么用 JSON 导入练习？**

一个 JSON 对象可以同时表达题干、多个选项、多个可接受答案和解释。出题工具和 Grace 可以共用这份格式。CSV 对简单题目很方便，但遇到多个选项和答案时，需要额外约定列的含义。

**07.2　一份 100 题的卷子中，第 80 题格式错了，会保存前 79 题吗？**

后端先校验整份文件，检查题型、标识和答案字段。通过后才开事务写入。校验失败会返回具体问题，题库里不会留下前半份卷子。

**07.3　上传后网络断开，为什么界面让用户先查题库？**

请求可能已经提交，只是浏览器没收到确认。系统允许同一文件生成两份独立试卷，所以自动重试可能制造副本。先查题库可以判断是否需要重新上传。

依据见[上传界面](../frontend/src/App.tsx)、[格式规则](../backend/src/papers/rules.rs)、[入库事务](../backend/src/papers/store.rs)。

### 08 按主题用 AI 出题

**08.1　用户要求五道关系从句题，系统怎样保证数量和题型？**

Rust 检查输入后，把主题、数量和选中的题型传给云函数。模型返回后，后端重新解析试卷，核对题数、允许的题型及每种所选题型是否出现。全部通过才保存。

**08.2　模型返回合法 JSON，就代表卷子合格吗？**

还要通过导入试卷使用的结构与字段校验。即使结构正确，程序也不能据此证明每道题的法语都准确，或者难度一定符合用户预期。

**08.3　为什么把出题放进 DigitalOcean Function？**

模型密钥和调用逻辑集中在 Function，Rust 继续负责会话、并发限制、校验和保存。直接从 Rust 调用也可行，可以少一次网络往返，但模型凭据和调用逻辑会进入应用部署。

依据见[生成入口](../backend/src/papers/generate.rs)、[Function](../functions/packages/grace/explain-answer/index.js)。

### 09 文件夹、移动试卷与删除

**09.1　删除文件夹会同时删掉里面的卷子吗？**

删除文件夹后，数据库把其中试卷的 folder_id 设为空。试卷会回到个人题库的根目录，答案和练习进度仍然保留。

**09.2　为什么同一用户不能同时建 Grammar 和 grammar 两个文件夹？**

数据库按所有者和转换成小写的文件夹名建立唯一索引。这能防止大小写造成的重复目录，也能处理两个页面同时创建同名目录的情况。

**09.3　为什么选文件夹？同一份卷子既属于 B1 又属于关系从句怎么办？**

当前每份卷子只有一个目录位置，移动和浏览都简单。如果需要同时按级别和语法点分类，标签更合适，需要增加试卷与标签的多对多关系。

依据见[题库界面](../frontend/src/PaperLibrary.tsx)、[文件夹操作](../backend/src/papers/folders.rs)、[数据库约束](../backend/migrations/0005_paper_library.sql)。

### 10 学习总览与继续练习入口

**10.1　点击 Continue 时，应用怎样决定打开哪份卷子？**

总览优先选择最近有练习活动的试卷，打开服务器保存的位置。如果还没有活动记录，会优先选择默认卷。题库为空时，页面提供上传入口。

**10.2　主页的 Questions answered 是提交次数吗？**

它统计当前题库中有已保存答案的题目数。对同一题提交三次仍只算一题，改答会改变这道题的当前对错状态。

**10.3　如果另一台设备恰好在我打开总览时交卷，页面会混合新旧数据吗？**

后端在同一个可重复读事务中读取试卷、进度和答案，所以这一次返回内部一致的快照。如果另一台设备稍后提交，下一次重新读取才会显示更新。

依据见[题库快照](../backend/src/papers/mod.rs)、[总览选择规则](../frontend/src/Overview.tsx)。

### 11 移动端导航与显示主题

**11.1　手机和桌面端是否各维护一套题库？**

两者使用同一个 React 应用和同一组 API。宽屏显示侧栏，窄屏按需展开题库。账号中的试卷与答案都从同一后端读取。

**11.2　刷新后主题为什么还在？换一台设备也会跟随吗？**

手动选择的主题保存在浏览器 localStorage，同源标签页可以同步。换设备后会使用该设备的本地偏好。若要跨设备保存，需要将设置关联到账号。

**11.3　用户选了跟随系统，再切换操作系统的深色模式会怎样？**

页面监听系统配色变化，并更新当前主题。用户如果明确选了浅色或深色，就按手动选择显示。这个行为可以在不刷新页面时验证。

依据见[界面布局](../frontend/src/App.tsx)、[主题设置](../frontend/src/components/theme-provider.tsx)。

## 答题与学习记录

### 12 作答、切题与回看

**12.1　为什么选择题提交 ID，翻译题却提交原文？**

选项已有稳定的标识，服务器可据此检查它是否属于本题，并比对正确选项。翻译和造句需要保存学习者实际输入的文字，供判分和回看。

**12.2　切到下一题，刚打了一半的句子会怎样？**

在同一练习页面内，未提交文字按题号存在前端草稿里，切回来可以继续。离开该页面或刷新后，服务器只会恢复已经提交的答案。

**12.3　如果用户快速连续点击几个题号，位置写入会乱序吗？**

同一页面把进度请求排队，并用上一笔成功保存后的版本号发送下一笔。这样同一标签页的切题按队列顺序保存。跨设备写入还要由服务器检查版本。

依据见[练习界面](../frontend/src/Practice.tsx)、[作答 API](../backend/src/practice/mod.rs)。

### 13 自动判卷

**13.1　演示中的 où 如果写成 ou，Grace 会判对吗？**

要看题型。如果是选择题，两个选项用不同 ID，只有正确选项得分。如果是文本题，当前规则会去掉重音，所以参考答案 où 和输入 ou 会匹配。这是宽松判分在法语重音练习上的局限。

**13.2　语法正确的同义句也可能被判错吗？**

可能。翻译题和造句题会把输入规范化，然后与出题人列出的可接受答案逐一比较。换一种正确表达，如果规范化后仍与所有参考答案不同，就会被判错。

**13.3　为什么没有让 AI 判所有答案？**

选择题和预设答案题可在本地按固定规则判分，同一输入会得到相同结果，也没有外部调用延迟。开放式写作更适合考虑模型评分，但需要评分标准和人工校准样本。

依据见[判分规则与测试](../backend/src/practice/rules.rs)。

### 14 即时反馈、成绩汇总与结束练习

**14.1　什么时候能看到参考答案和题目解释？**

首次打开未答题时，服务端返回题干和选项。提交后，响应才包含对错、参考答案和题目自带的解释。重新打开已答题也能看到这些反馈。

**14.2　三个问题答对一个、答错一个，还有一个没答，成绩怎么变？**

此时汇总为正确 1、错误 1、未答 1。把错题改对后，会变成正确 2、错误 0、未答 1。统计依据是每题最新保存的答案。

**14.3　点 Finish 后还能改答案吗？**

可以。Finish 汇总当前结果，并更新已有练习记录的活动时间。产品定位是反复练习。如果用于正式考试，还需要增加场次、交卷锁定和独立成绩记录。

依据见[作答与结束接口](../backend/src/practice/mod.rs)、[试卷详情](../backend/src/papers/mod.rs)。

### 15 AI 讲解已提交答案

**15.1　AI 怎样知道我选了什么？浏览器可以自己指定要解释的答案吗？**

点击 Explain 时，浏览器提交的是针对该题的请求。后端检查用户和试卷，从数据库取出已保存的答案，并将选择题的选项 ID 转成可读文字后交给 Function。

**15.2　既然每题已有解释，为什么还要提供 Explain？**

试卷自带的是固定说明，提交后立即可见。额外讲解会把题干、学习者答案、参考答案和已算出的对错一起交给模型，让它解释这一次作答。

**15.3　如果模型超时或讲错了，学生的成绩会变吗？**

成绩在提交答案时就已由 Rust 判定并保存。Explain 是独立的只读操作，调用失败可以显示错误，模型输出也没有修改分数的写入路径。

依据见[讲解请求](../backend/src/practice/explain.rs)、[Function](../functions/packages/grace/explain-answer/index.js)。

### 16 保存答案、题号与跨设备续练

**16.1　为什么答案、判分和当前位置要一起提交？**

它们描述同一次作答。数据库事务让三者一起成功或一起撤销，避免重新登录后看到题号已经前进，但答案还没保存。

**16.2　今天用手机答第二题，明天电脑怎样找到它？**

电脑登录同一账号后读取试卷详情。后端按用户和试卷查出已保存的位置，再取出对应答案和判分。电脑无需拿到手机里的缓存。

**16.3　如何证明答案已写到服务器，而不是浏览器记住了界面？**

可在同一账号的独立浏览器会话中重新打开试卷，核对题号、答案和统计。现有 Compose 测试也用另一个会话读回这些数据，这一步验证了跨会话保存。

依据见[写入事务](../backend/src/practice/mod.rs)、[进度与答案](../backend/src/practice/store.rs)。

### 17 两台设备同时修改的冲突处理

**17.1　两台设备都读到版本 7，然后同时提交，结果是什么？**

先成功更新数据库的一笔把版本推进到 8。另一笔仍要求版本为 7，会收到 HTTP 409。页面重新加载当前进度，并提示用户复核后决定是否再提交。

**17.2　两台设备改的是不同题，为什么也可能发生冲突？**

版本号属于整份用户试卷，两个请求还可能同时修改“当前题号”。这种设计用一条规则保护答案和位置。若要并行编辑不同题，可给每题单独版本，再定义位置冲突如何处理。

**17.3　为什么不自动重放发生冲突的答案？**

服务器已经确认另一台设备写入了新状态。若自动用旧操作覆盖，可能把位置移回去或抹掉刚改过的答案。让用户看到最新结果再提交，可以保留他们对这次修改的选择。

依据见[版本检查](../backend/src/practice/store.rs)、[页面队列和冲突提示](../frontend/src/Practice.tsx)。

### 18 有效学习时长

**18.1　开着练习页去吃饭，午餐时间会计入吗？**

页面只在前台且获得焦点时计时。切后台会暂停，保持前台但无输入时最多计到最近一次输入后的两分钟。它估算活跃练习时间，无法精确测量注意力。

**18.2　手机记了 10:00 到 10:02，电脑记了 10:01 到 10:03，总共几分钟？**

对同一账号是三分钟。后端在 PostgreSQL 中合并重叠时间区间，只计算两段覆盖的总时长。跨 UTC 午夜的区间会先按日期拆分。

**18.3　网络断开后为什么可能少记学习时长？**

浏览器约每 15 秒发送一段区间，当前实现失败后也会继续移到下一段。可改进为暂存未确认区间，并在服务端允许的时间窗口内重发。后端已有区间合并能力。

依据见[浏览器计时](../frontend/src/useStudyTime.ts)、[区间合并](../backend/src/practice/time.rs)。

## 应用与云架构

### 19 前端、后端与服务边界

**19.1　用户点一次答案，React、Auth、Papers 和 Practice 各负责什么？**

React 收集输入，Auth 从会话识别用户，Papers 找到该用户卷子里的题目，Practice 判分并写入数据库。三个后端模块在同一个 Rust 进程内调用。

**19.2　为什么没有把三个业务模块都拆成微服务？**

现有模块要共同完成一次答题，进程内调用容易追踪，也方便用一个数据库事务保存结果。拆开以后能独立部署，但要承担跨服务调用和一致性处理。

**19.3　哪些组件确实可以独立于学习应用运行？**

运维面板有独立的进程和 Pod，数据库有独立的 StatefulSet，AI 在 DigitalOcean Function 中执行。因此普通答题绕开模型服务，扩应用副本也无需复制整个数据库。

依据见[应用入口](../backend/src/main.rs)、[镜像构建](../Dockerfile)、[运维进程](../backend/src/bin/dashboard/main.rs)。

### 20 容器化与本地开发

**20.1　Docker 镜像里为什么既有 Rust 程序又有前端静态文件？**

构建阶段分别编译 Rust 和打包 React，最终镜像带上可执行文件与静态资源。发布一次即可让页面和 API 来自同一应用版本，运行容器无需安装前端构建工具。

**20.2　本地已经能用 Compose，为什么还要 minikube？**

Compose 足以验证应用连接 PostgreSQL 和基本用户流程。minikube 可以运行真实的 Kubernetes Service、HPA、探针和 PVC，适合在上云前重现调度与扩容行为。

**20.3　重建本地应用容器，练习数据会丢吗？**

只重建应用时，数据库继续保存数据。重建数据库容器时，只要重新挂载原来的命名卷，也能读回数据。删除数据卷会改变这个结果。

依据见[Dockerfile](../Dockerfile)、[Compose](../compose.yaml)、[本地集群配置](../k8s/minikube/kustomization.yaml)。

### 21 集群编排与云平台选择

**21.1　你们为什么最终选 Kubernetes，而没有选 Docker Swarm？**

团队比较过两套原型。Swarm 接近已有的 Compose 环境，上手更快。Grace 还需要卷重新挂载、按负载扩容和定时备份。Kubernetes 用 PVC、HPA 和 CronJob 表达这三件事，团队接受了额外的配置和排障工作。

**21.2　如果坚持用团队当时的 Swarm 方案，主要要补什么？**

原型的数据库使用节点本地卷，因此要约束数据库运行位置，或另配可跨节点使用的存储。CPU 扩容要接监控并编写调副本脚本，定时备份也需要另外的调度方式。

**21.3　minikube 和 DigitalOcean Kubernetes 怎样共用一套部署定义？**

Kustomize 的基础清单描述共同的应用、Service、数据库和 HPA。环境配置再覆盖镜像、存储和入口。这样两端共享资源结构，同时允许本地和云端有不同的基础设施。

依据见[基础资源](../k8s/base/kustomization.yaml)、[云端配置](../k8s/doks/kustomization.yaml)、[提案中的两套原型与选择依据](../proposal.md)。

### 22 HTTPS 入口与流量分发

**22.1　一次 HTTPS 答题请求经过哪几层？**

浏览器先连接 DigitalOcean Load Balancer，流量转到 Caddy。Caddy 终止 HTTPS，再把请求交给应用 Service，由它路由到就绪的 Rust Pod，最后由后端访问 PostgreSQL。

**22.2　外部已经有负载均衡器，为什么还需要 Kubernetes Service？**

两层解决不同的寻址问题。外层提供稳定的公网入口。应用 Service 在集群内提供稳定地址，并随着 Pod 就绪或退出而更新后端集合。Caddy 不需要保存每个 Pod 的地址。

**22.3　为什么 Caddy 也申请了持久卷？**

Caddy 在卷上保存证书状态，重建后可继续使用。当前云端入口只有一个 Caddy 副本，因此应用层有多个副本，入口层仍有单实例带来的可用性限制。

依据见[云端入口](../k8s/doks/caddy.yaml)、[Caddy 路由](../k8s/doks/Caddyfile)、[应用 Service](../k8s/base/app.yaml)。

### 23 应用自动扩缩容与可用性

**23.1　HPA 的 70% 到底是哪个数的 70%？**

是应用 Pod 平均 CPU 使用量相对于 CPU request 的比例。每个应用 Pod 请求 100m CPU，目标 70% 对应平均约 70m。这里的分母不是整台节点的 CPU 容量。

**23.2　HPA 要五个副本时，为什么面板可能只看到三个可用？**

目标副本数表示期望状态。新增 Pod 还要完成调度、启动并通过就绪检查，才会成为可用副本。面板分别记录首次提高目标副本数和达到五个可用副本的时间。

**23.3　若慢在模型或数据库，多开应用 Pod 能解决吗？**

不一定。AI 请求等待上游时，应用 CPU 未必升高。数据库饱和时，更多应用副本还可能增加连接压力。需要同时看业务延迟、CPU、数据库连接和实际吞吐。

依据见[HPA 策略](../k8s/base/hpa.yaml)、[CPU 请求与就绪检查](../k8s/base/app.yaml)、[数据库副本](../k8s/base/postgres.yaml)。

### 24 PostgreSQL 与持久存储

**24.1　StatefulSet 和 PVC 分别为 PostgreSQL 提供什么？**

StatefulSet 给数据库 Pod 稳定的身份，并按声明管理其存储。PVC 让新 Pod 可以挂载同一块持久卷。数据库文件保存在卷上，Pod 的生命周期可以比数据短。

**24.2　为什么没有直接使用托管 PostgreSQL？**

课程要求团队展示持久存储的实现。集群内运行 PostgreSQL 并绑定 DigitalOcean 块存储，可以直接演示 Pod 更换后重新读取原数据。相应地，团队也承担数据库备份和恢复责任。

**24.3　数据库 Pod 所在节点出问题，用户体验会怎样？**

当前只有一个数据库实例。重新调度、重新挂卷和启动期间，依赖数据库的请求可能失败。原卷能帮助保留数据，但要缩短数据库故障切换时间，还需要主备复制和切换机制。

依据见[数据库配置](../k8s/base/postgres.yaml)、[云端存储类](../k8s/doks/kustomization.yaml)、[基础表结构](../backend/migrations/0001_init.sql)、[课程要求](../requirements/requirements.md)。

### 25 数据库迁移与连接管理

**25.1　滚动发布时，两个新 Pod 同时启动，会重复执行迁移吗？**

应用先取得 PostgreSQL 事务级 advisory lock，再读取已执行版本。一个 Pod 完成迁移并提交后，另一个取得锁，看到该版本已有记录就跳过。

**25.2　为什么每个 Pod 的数据库连接池限制为 10？**

每个副本都持有自己的池，扩容会叠加连接数。上限为 10 时，五个应用副本的池合计最多 50 个连接，还要为滚动更新和其他数据库客户端留余量。

**25.3　如果刚加的数据库字段要取代旧字段，怎样让滚动发布可回退？**

可分两次发布。先新增字段并让新旧版本都能读写，等数据迁完、旧 Pod 退出并过了回退窗口，再删除旧字段。这样旧应用镜像仍有兼容的数据结构可用。

依据见[启动与连接池](../backend/src/main.rs)、[迁移目录](../backend/migrations)。

### 26 环境配置与密钥管理

**26.1　哪些配置适合放 ConfigMap，哪些要用 Secret？**

域名、允许的来源和环境名称放 ConfigMap。数据库密码、邮件凭据和 Function 调用凭据通过 Secret 注入使用它们的容器。前端代码会发给浏览器，因此不能用来保管服务端密钥。

**26.2　浏览器和 Rust 后端都需要 OpenAI 密钥吗？**

都不需要。浏览器调用 Grace，Rust 用自己的调用凭据访问 DigitalOcean Function，Function 才读取 OpenAI 密钥。不同组件只接收各自需要的凭据。

**26.3　更新 SendGrid Secret 后，正在运行的 Pod 会立即生效吗？**

这里通过环境变量注入，旧进程仍持有启动时的值。更新 Secret 后还要滚动重启应用，让新 Pod 读取新值，再验证邮件投递。

依据见[应用配置](../k8s/base/app.yaml)、[DOKS 配置](../k8s/doks/kustomization.yaml)、[Function 环境](../functions/project.yml)、[CI 环境](../.github/workflows/grace.yml)。

## 监控与演示

### 27 健康检查与服务就绪

**27.1　startup、liveness、readiness 三种探针分别解决什么问题？**

startup 给启动和迁移留时间。liveness 检查进程能否继续响应，持续失败可触发重启。readiness 判断当前是否适合接流量，应用的就绪检查还会限时查询数据库。

**27.2　数据库短暂离线，为什么不把所有应用 Pod 都重启？**

重新启动 Rust 进程无法修复独立数据库。Grace 让数据库故障体现在 readiness 上，暂时移出不可服务的副本，同时保留仍能响应的应用进程，等依赖恢复。

**27.3　用户侧探针和 Pod 探针都访问健康端点，有什么差别？**

Pod 探针用于 Kubernetes 的重启和路由决策。演示脚本从配置的应用入口定期请求 readiness，记录该位置看到的成功或失败和耗时，因此可以观察入口路径上的中断。

依据见[应用探针](../k8s/base/app.yaml)、[就绪逻辑](../backend/src/main.rs)、[外部采样](../scripts/dashboard-demo.py)。

### 28 实时集群拓扑与 Pod 事件

**28.1　拓扑图怎样知道哪个 Pod 真能接收 Service 流量？**

面板监听 Kubernetes 资源，结合 Service、EndpointSlice 和 Pod 状态画连线。新 Pod 出现在节点图上，只说明它已被观察到。成为可路由端点后，才应看到对应的流量路径。

**28.2　为什么实时面板使用 SSE？用 WebSocket 可以吗？**

主要流量是服务器把集群状态推给浏览器，浏览器用 EventSource 接收快照和更新即可。WebSocket 也能完成，但当前订阅主要是单向的，启动、停止等少量控制操作已有普通 HTTP 接口。

**28.3　心跳还在跳，可以判定所有 Kubernetes 数据都是最新的吗？**

心跳表示浏览器仍连着面板服务。面板还记录各类资源的同步状态和更新时间。判断数据新鲜度要看这些同步信息，不能仅凭最近收到心跳的时间。

依据见[集群监听](../backend/src/bin/dashboard/cluster.rs)、[SSE](../backend/src/bin/dashboard/main.rs)、[可读资源权限](../k8s/monitoring/access.yaml)。

### 29 性能指标与历史曲线

**29.1　Prometheus 和实时拓扑各回答什么问题？**

Kubernetes 监听适合回答“现在有哪些 Pod，谁已就绪”。Prometheus 时间序列适合回答“过去几分钟 CPU、流量和副本数怎样变化”。把两者放在一起，才能将资源变化与负载走势对齐。

**29.2　面板上答题平均延迟正常，可以断定大多数慢请求都消失了吗？**

不能。面板用累计答题处理时间和次数计算均值，少数慢请求可能被掩盖。要看尾部延迟，可以看对照实验的 p95，或为长期监控增加延迟直方图。

**29.3　Pod 入站和出站流量曲线能直接换算成答题次数吗？**

不能。曲线统计应用 Pod 网络接口的流量，也覆盖数据库和监控通信。要看答题次数，应看答题接口的业务计数，再用网络曲线解释整体流量变化。

依据见[采集配置](../k8s/monitoring/prometheus-values.yaml)、[指标查询](../backend/src/bin/dashboard/metrics.rs)、[应用指标](../backend/src/observation.rs)。

### 30 操作日志、请求追踪与筛选

**30.1　用户报告一次提交失败，如何定位到那一笔？**

从该响应的 X-Trace-Id 取得标识，在运维日志里按 Trace ID 筛选。记录会显示处理它的 Pod、响应状态和已有的处理阶段，可以判断错误发生在查题、判分还是保存阶段。

**30.2　一次界面操作如果发了多个请求，如何把它们放在一起看？**

前端可以给相关请求附上同一个操作 ID。每个请求仍有独立的 Trace ID。前者帮助还原用户操作，后者定位单个 HTTP 请求。

**30.3　数据库暂时不可写，日志会永久完整地保留下来吗？**

应用先输出结构化 Pod 日志。数据库写入失败后，会把事件放入有界内存队列重试。队列有容量上限，进程重启也会丢掉内存，因此七天查询窗口不等于每次故障下都保证零丢失。

依据见[采集与重试](../backend/src/observation.rs)、[日志查询](../backend/src/devops.rs)、[日志界面](../dashboard/logs.js)。

### 31 公开状态页与受限运维面板

**31.1　公开状态页和登录后的运维页分别能看到什么？**

访客得到筛选后的集群快照和指标。详细操作日志、请求处理阶段和已启用的负载测试控制需要运维账号。服务器为两个入口准备不同的响应内容。

**31.2　为什么把按钮在前端隐藏还不够？**

页面展示只能决定用户看到什么。真正的权限边界在服务器，受限路由会验证会话和运维角色，公开入口也只转发允许的读取路径。这样更换客户端不会改变访问权限。

**31.3　面板为什么使用独立的 Kubernetes ServiceAccount？**

它只需要读取用于拓扑的资源和有限的日志。独立账号可以把集群级节点读取和命名空间内资源读取分开授权，无需给面板管理 Deployment 或读取 Secret 的权限。

依据见[公开路由](../k8s/doks/Caddyfile)、[运维授权](../backend/src/devops.rs)、[访客快照](../backend/src/bin/dashboard/main.rs)。

### 32 登录分流与一键扩容演示

**32.1　十次并发登录怎样证明两个 Pod 都处理了流量？**

演示客户端为请求分配标识，并记录返回结果。面板把这些标识与应用 Pod 的日志关联。PPT 中十次均成功，两个 Pod 分别处理七次和三次，这能证明两个副本都参与了该轮处理。

**32.2　十次登录为什么没有刚好五五分？**

Service 不承诺在十次请求内平均分配。连接复用和当时可用的端点都会影响分布。这次演示要核对的是请求成功、可归属到 Pod，以及多个副本实际参与服务。

**32.3　关闭浏览器后，一键扩容演示会一直消耗 CPU 吗？**

负载由服务端控制。应用 Pod 需反复取得短期授权才会继续产生 CPU 负载。达到五个可用副本、手动停止或三分钟超时后，面板停止发放授权。该演示验证的是 HPA 控制流程。

依据见[登录演示](../scripts/dashboard-demo.py)、[CPU 负载](../backend/src/demo_cpu.rs)、[停止条件](../backend/src/bin/dashboard/load_test.rs)。

### 33 业务负载与扩容效果对照

**33.1　固定两个 Pod 和开启 HPA 的实验怎样比较？**

在同一个两节点 minikube 集群，用十个专用账号执行相同流程，包括登录、读卷、提交、保存位置、重开核对和登出。分别运行固定两个副本和允许 2–5 个副本的配置，记录实际吞吐、延迟和数据库连接。

**33.2　每秒安排 120 个流程时，HPA 提升了多少吞吐？**

这次没有提升。固定两个 Pod 实际完成 83.75 个流程/秒，HPA 完成 79.89 个/秒，后者在 15 秒采样时已有五个可用 Pod。每秒安排 60 个流程时，两种配置都完成约 60 个/秒。这里的单位是完整流程，每个流程包含七个 HTTP 操作。

**33.3　已启动流程的失败率为零，为什么不能说系统承受了每秒 120 个流程？**

每个账号一次只执行一个流程。上一次还没结束时，下一次计划启动会被跳过。固定副本组跳过 5,429 次，HPA 组跳过 6,010 次。零失败率只描述已启动的流程，这组本地数据也不足以确定云端容量或瓶颈。

依据见[实验脚本](../scripts/compare-practice-hpa.py)、[结果与限制](../dashboard/evidence/practice-pressure.md)。

## 发布与恢复

### 34 持续集成与验收测试

**34.1　一个面向 dev 的 PR 需要通过哪些验证？**

GitHub Actions 运行 Rust 单测、Function 契约测试、前端 lint 和部署清单渲染。随后构建应用镜像，连接临时 PostgreSQL 17，检查静态资源并运行 HTTP 业务测试。PR 触发验证，合入后的 dev 推送可再触发部署。

**34.2　为什么要用真实 PostgreSQL 做集成测试？**

有些关键行为依赖数据库本身，例如唯一约束、事务、外键和并发版本更新。临时 PostgreSQL 可以验证两个会话或两个用户通过真实 API 操作时，系统是否仍满足这些约束。

**34.3　CI 通过，能说明线上邮箱注册、登录和答题都测过了吗？**

不能。隔离的 Compose 测试使用预建会话，对题库和作答做业务检查。线上冒烟检查覆盖公开页面、健康状态和匿名权限。真实邮件投递、浏览器交互和线上登录后的读写需要其他证据。

依据见[工作流](../.github/workflows/grace.yml)、[业务测试范围](../tests/smoke.py)、[Function 测试](../tests/generate-paper.cjs)。

### 35 镜像版本、滚动发布与上线验证

**35.1　从 PR 合入到学习者看到新页面，中间经历什么？**

对 dev 的推送先重新验证，再核对该提交是否仍是分支最新提交。流水线发布经过测试的镜像，以镜像摘要渲染 DOKS 清单，执行滚动部署，最后检查副本、存储和公开站点。

**35.2　连续合入两个 PR，怎样降低旧流水线覆盖新版本的风险？**

部署脚本在关键步骤重新读取 GitHub 上 dev 的最新提交。如果这次运行已被后续提交取代，就跳过后续发布步骤。这个检查尤其适合两次构建耗时不同的情况。

**35.3　应用镜像发布成功，是否也更新了 DigitalOcean Function？**

应用流水线会测试 Function 的请求和响应契约。运行在 DigitalOcean 上的 Function 有独立的部署配置和发布动作。应用镜像上线本身不能证明线上 Function 已更新。

依据见[发布脚本](../scripts/deploy-dev.sh)、[版本计算](../scripts/release-version.sh)、[工作流](../.github/workflows/grace.yml)、[Function 配置](../functions/project.yml)。

### 36 发布失败回滚

**36.1　新版本部署后验收失败，脚本如何恢复应用？**

发布前先保存旧应用镜像及首页。若应用仍运行本次目标镜像，而且旧镜像与它不同，脚本会切回旧镜像，等待 rollout 完成，再检查就绪端点并比对之前的首页。

**36.2　回滚旧镜像，刚执行过的数据库迁移也会自动撤销吗？**

不会。脚本恢复的是应用 Deployment 中的镜像。数据库结构和已经写入的数据需要单独处理，因此发布涉及迁移时，应提前确保旧版本还能读写新结构。

**36.3　应用已经验收成功，随后监控部署失败，学习者会被切回旧版吗？**

这条路径在应用验收后已经解除应用回滚处理。监控失败会让发布检查报告失败，但已验证的学习应用继续运行，团队可以单独修复监控。

依据见[回滚条件与检查](../scripts/deploy-dev.sh)。

### 37 定时备份、私有存储与保留

**37.1　每天 05:00 的备份从数据库怎样到达 Spaces？**

CronJob 按多伦多时区调度。第一个容器用 pg_dump 生成自定义格式归档并检查归档目录，第二个容器把文件上传到私有 Spaces，再核对远端大小。两个容器通过同一个临时工作卷交接文件。

**37.2　今天上传失败，脚本还会删除七天前的备份吗？**

不会。上传和大小检查都成功后，才进入保留期清理。清理只处理指定前缀下符合条件的旧归档，并跳过本次新上传的对象。

**37.3　有每日备份，就能把数据库恢复到今天 14:37 吗？**

目前可以恢复到选定逻辑备份所包含的状态。若最近一次成功备份在 05:00，单靠该归档无法恢复之后的数据。要针对 14:37 做时间点恢复，需要基础备份配合连续 WAL 归档等机制。

依据见[CronJob](../k8s/doks/backup.yaml)、[备份与保留脚本](../k8s/doks/backup.sh)。

### 38 备份恢复与重启后的持久化验证

**38.1　现场重启数据库后答案还在，这项演示证明什么？**

它证明替换数据库进程或 Pod 后，应用能从原来的持久卷重新读到答案和题号。整个过程仍使用原卷，因此还需要独立的恢复演练，才能检验 Spaces 里的归档。

**38.2　怎样证明一份备份真的能恢复学习服务？**

按手册选取归档，恢复到独立空库，再让测试应用连接它。登录已有测试账号，依次核对试卷、已保存答案和当前题号。这样能同时检查归档可读、表关系可用和应用能解释恢复的数据。

**38.3　如果答辩老师问实际恢复用了几分钟，应该报哪个数字？**

当前材料给出了恢复步骤，没有给出这一版本一次完整恢复演练的实测总时间。可以说明测量口径是从选定归档开始，到测试账号能读回正确答案和题号为止。只有完成计时演练后，才能报告实测时长。

依据见[恢复手册](../k8s/doks/README.md)、[面板演示说明](../dashboard/README.md)。
